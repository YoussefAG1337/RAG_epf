- (direction) Create a specification only; do not implement the application.
- (decision) First version serves one course from a fixed collection of searchable PDFs through a student chat interface.
- (capability) CAP-1: Ingest the fixed PDF collection through a local command; success requires searchable page-linked chunks and an idempotent rerun.
- (capability) CAP-2: Answer student questions using retrieved evidence from the selected course only; success requires no unsupported general-knowledge answer.
- (capability) CAP-3: Stream answers to the student chat interface; success requires incremental answer rendering and a clear completion or failure state.
- (capability) CAP-4: Cite every supported answer with source filename and PDF page number; success requires each substantive claim to be traceable to displayed evidence.
- (capability) CAP-5: Show citation cards with supporting excerpts; success requires students to inspect the evidence associated with each citation.
- (capability) CAP-6: Refuse unsupported or insufficiently supported questions; success requires an explicit materials-insufficient response without model-supplied facts.
- (capability) CAP-7: Preserve course boundaries in stored documents, chunks, retrieval, and answering; success requires course_id filtering even though v1 exposes one course.
- (capability) CAP-8: Evaluate factual, multi-passage, ambiguous, and unsupported questions; success requires a repeatable local evaluation dataset and result output.
- (constraint) Backend must use Python FastAPI with direct pypdf, SQLAlchemy, Alembic, and Pydantic integration; LangChain and LlamaIndex are excluded.
- (constraint) Frontend must use Next.js and provide the unauthenticated student chat experience.
- (constraint) Persistence must be PostgreSQL with pgvector operated through Docker Compose.
- (constraint) Gemini API must provide embeddings and answer generation.
- (constraint) Documents must store checksums, and re-ingestion must be idempotent.
- (constraint) Every supported answer must cite filename and PDF page number; absent sufficient evidence, the system must abstain.
- (constraint) V1 excludes authentication, instructor UI, deployment, OCR and scanned PDFs, audio, video, monitoring, and separate environments.
- (assumption) Searchable PDFs contain extractable text and stable file-level page ordering suitable for pypdf extraction.
- (assumption) The local ingestion command reads from a configured local directory and synchronizes only explicitly supplied PDFs.
- (question) Which Gemini embedding and generation model identifiers and dimensions should be the v1 defaults?
- (question) Should cited page numbers use one-based physical PDF pages, printed page labels, or both when they differ?
- (question) What quantitative acceptance threshold should the evaluation suite enforce, if any, beyond case-by-case expected behavior?
- (note) Wrapper-only content: the request to use bmad-spec and collaborate interactively affects process, not the product contract.

- (event) Self-validation pass 2 (preservation): PASS; every load-bearing product, technology, scope, ingestion, citation, grounding, streaming, course-scoping, and evaluation requirement from the user brief appears in SPEC.md or a named companion.

- (decision) Resolved model defaults: answer generation uses gemini-3.8-flash; embeddings use gemini-embedding-2 with 768 output dimensions.
- (constraint) Embedding model and output dimensionality form one coupled database schema decision; changing either requires re-embedding every chunk and applying an appropriate database migration.
- (decision) Resolved citation numbering: V1 uses one-based physical PDF page numbers; printed page labels are unsupported.
- (decision) Resolved evaluation acceptance: every deterministic check must pass; semantic results remain visible case by case and require manual acceptance, with no aggregate numerical threshold in V1.
- (note) The three prior open questions are resolved by the model, citation, and evaluation decisions recorded in this update.
